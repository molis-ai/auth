## 2 工具与复现

在 Auth 根目录运行，Node.js 22.18+。首次使用真实 WASM 集成测试前先执行 `npm --prefix worker run build:rust`。两条演练命令的输出目录必须不存在；只生成自己的合成数据库，不接受既有数据库作为写入目标。

```sh
# 合成 Auth：盘点、备份、切换、重试、回退、重试、离线恢复核对
npm run account:migration -- rehearse /private/tmp/auth11-example

# 只读盘点合成数据库；将来读取真实副本须另行授权
npm run account:migration -- inventory AUTH /private/tmp/auth11-example/synthetic-auth.sqlite

# 直接复用 Club 的迁移与映射 owner，Club 路径须为包含 CLUB-08 的检出
npm run account:migration:club -- /absolute/path/to/molis-club /private/tmp/auth11-club-example
npm run account:migration -- inventory CLUB /private/tmp/auth11-club-example/synthetic-club.sqlite

# SQLite 工具测试 + 真实 WASM / 临时 D1 专项
npm --prefix worker run test:migration
```

源码入口为 `worker/scripts/account-migration.mjs`、`worker/scripts/account-migration/` 和 `worker/scripts/rehearse-club-mapping.mjs`。没有远程参数、网页导入接口，或对任意现有数据库执行切换/回退的 CLI。内部切换函数仅用于合成演练，要求合成标记、明确的产品登记、LOCAL 环境、mock 发送与提供方、本机 Auth 地址；它不是生产迁移执行器。

盘点以 SQLite 只读模式打开离线文件，拒绝直接读取 `.wrangler`、`.molis` 路径。输出结构/源数据摘要、迁移日志（若存在）、账号与 Client ID、邮箱可信标记、密码格式分类、提供方与稳定标识存在性、同邮箱/外部身份冲突组、旧 TEAM 和角色、外键异常。未知密码只标待处理，不推测算法。报告不输出邮箱、密码哈希、Token、外部 subject 或留言正文；ID 和审核记录仍按内部资料保管。

合成输出目录权限为 `0700`，数据库与 JSON 为 `0600`。Auth 输出 `inventory-before.json`、`reviewed-plan.json`、`inventory-after.json`、`rehearsal-report.json`，以及运行库、备份库和独立恢复库。Club 输出合成 Auth/Club 库和 `club-mapping-report.json`。备份通过 SQLite backup 取得一致快照，恢复到另一个离线文件，核对源摘要、数据库完整性和外键；不会覆盖切换后数据库。

源摘要用于审核时发现数据变化，不能代替账号归属证明。生产切换还需停写窗口，避免盘点与执行之间的身份变化；目前不提供在线不停写迁移。演练中的审核人和证据均为夹具生成，不代表真实账号已审核。

## 3 账号接续决定

| 情形 | 处理方案 | 本轮证明范围 |
| --- | --- | --- |
| 已在 Auth，密码格式受支持且邮箱已验证 | 保留中央 user ID、密码哈希及资料，新产品重新登录到同一主体 | 真实 WASM/D1 中 Work、Club 使用合成旧密码取得同一旧 user ID |
| Auth 邮箱未验证 | 保持未验证状态；有其他可用方式时按正常自助流程处理。没有可用方式的列为待处理 | 已证明 v2 密码登录拒绝，未修改可信度。切换前须确定专门的旧账号补验证路径；当前新注册/找回流程不能被当成已交付的存量补验证方案 |
| 未识别密码格式或 Club 独立密码 | 保留原哈希和来源；核对算法/参数、账号归属及合适的验证/重设路径，再决定是否开发专门接续适配 | 不复制不明哈希到 Auth，不承诺 Club 原密码已可用于中央登录 |
| 第三方账号 | 对照 issuer、subject 和原应用登记；已有可信关联才能接续。同邮箱、昵称或 avatar 不能作为归属证明 | mock issuer 与真实 Google/GitHub issuer 分开，模拟登录不能证明真实身份接续；Apple 的处理待确认 |
| Club 旧用户已有可证明的中央主体 | 用 Club owner 的 `LINK` 决定建立 `(issuer, auth_user_id) → 原 user.id` | 复用 `applyBusinessIdentityDecision`，重复幂等、冲突拒绝；旧资料、验证标记、凭据、会话行、留言外键和署名逐值保留 |
| 明确为全新的中央用户 | 审核为 `NEW` 后创建本地业务用户，邮箱可为 NULL | 不造占位邮箱；同邮箱待处理旧用户不会因此被认领。不能用 NEW 绕过旧用户归属争议 |
| 同邮箱多账号、身份冲突或证据不足 | 原记录全部保留，列待处理，不自动合并、不自动转移内容 | 合成冲突保留，无额外认领；首期不因此引入人工账号恢复 |
| 旧 TEAM | 平台核对成员、所有者与用途后另行制定纳管决定；受管租户仍只能由平台创建/分配 | 演练保留旧 TEAM、OWNER/VIEWER 等角色，不自动纳管、升级角色或赠送订阅席位 |

Club 审核文件的 `VERIFIED` 是可信运维记录，不是工具完成了密码验证。具体字段和证据枚举沿用 Club 的 `docs/BUSINESS-IDENTITY-MIGRATION.md`。本期没有自动解关联、覆盖映射或账户合并功能。已失去全部登录方式的账号继续遵守既定规则：用户先找回原登录方式，不因迁移开放人工恢复。

## 4 切换顺序与依赖

以下是实际切换的操作方案。AUTH-11 完成合成库中央切换，WORK-09 / CLUB-09 已补齐产品旧入口关闭、导航、Home 保留及联合回退验证；这些只在合成环境执行，真实切换还需实际盘点与审核。

1. **固定来源。** 记录实际部署提交、数据库标识/迁移日志、配置版本、完整旧 Client 集合、回调及缓存位置。只读取得获准的一致副本，备份校验并完成恢复演练。按账号决定表建立已接续/待补验证/冲突/不支持清单；关键归属或外键异常时停止，不跳过失败继续全量切换。
2. **准备新入口。** 为 Work/Club 登记独立 v2 Client、环境、产品和回调，初始停用。保留旧 Client 配置，明确可回退的产品版本。不要在同一 Client 上反复增删 v2 policy：新会话和相关外键需要保留。实际存在桌面等多个旧 Client 时须完整列出；当前合成引擎仅演练每个产品一对新旧 Client，真实多 Client 场景需扩展和复验，不能只停一个就声称完成。
3. **暂停受影响写入。** 产品进入受控切换状态，停止旧注册/绑定/改密和业务写入，取消在途旧登录与刷新，备份最终快照并重新审核摘要。只影响 Work/Club，不暂停其他产品。Club 在事务内执行自身表结构迁移和已审核映射；额外外键、视图、触发器或索引触发迁移拒绝时先复核。
4. **中央切换。** 同一 D1 batch 校验 Client、应用、产品与环境版本，停用旧 Client、启用新 Client、增加配置版本，并写审计回执。撤销目标旧 grant、消费旧授权码、取消旧登录事务；撤销目标新 Client 的预存会话与证明，避免暂存状态复活。失败全部回滚，成功重试返回原回执。
5. **切换产品。** Work Host 使用新会话存储，不读取旧 personal 凭据；取消旧回调/刷新，重启也不恢复旧登录。保留 Home、本地内容和 `LOCAL_PERSON_ACTOR_ID`。Club 停用旧 Better Auth 注册/登录/改密等入口及 Cookie 接受，切换至 BFF 中央会话；旧凭据行和历史数据继续保留。只有审核映射完成的旧业务身份才可写留言，未解决者显示待处理。
6. **核对并开放。** 重新登录核对中央 ID、Club 原 user ID/留言、Work 本地 Home；验证两端资料一致、旧令牌/回调拒绝及其他产品会话有效，复查外键、重复和待处理数量。具体放量条件依实际盘点确定；凭据接续不完整不能被“新账号可登录”替代。

v1 的 `auth_authentication` 是多个产品共享的根会话，`auth_grant` 才按 Client 区分。本次切换不能撤销共享根、修改全局用户安全 epoch 或调用“退出全部设备”，否则会误退其他产品。Client 清单来自部署登记与审核，不能按名称包含 work/club 自动猜测。

## 5 回退与失败停止

回退以恢复可用路由/配置并保存切换后数据为原则。已发生的密码、安全验证、账号创建、业务留言和审核映射不会因回退被删除。

| 时点/问题 | 操作 | 不变量 |
| --- | --- | --- |
| 中央 batch 任一步失败 | 整笔事务回滚，修复原因后用同一审核计划重试 | Client 状态、撤销与回执不能部分提交 |
| 已切换，决定回退 | 先暂停目标产品写入/新登录并取消回调；确认配置没有后续变更，再恢复旧 Client 状态、停用新 Client，版本继续递增；撤销这两组目标的会话/授权码/证明 | 不恢复任何旧令牌或旧 Cookie；其他产品会话继续有效。用户必须重新登录 |
| 回退 batch 中途失败 | 留在完整的已切换状态，保持产品维护状态，修复后重试 | 不出现一个产品已回退另一个未回退、或回执与实际状态不一致 |
| 切换后配置又被管理员修改 | 自动回退拒绝，重新审核当前配置后制定新的修复计划 | 不覆盖后续配置，不把版本降回旧值 |
| 已有新账号/绑定/密码修改/业务写入 | 保留新增身份、凭据事实、Club 映射和留言；优先配置回退或向前修复 | 不用旧备份覆盖在线库，不回滚安全撤销。无邮箱/新方式用户可能无法使用旧 UI，应维持受影响入口的维护状态直至修复 |
| Club 映射疑似错误 | 暂停相关业务访问，保留证据与原内容，重新核对两边归属后另审纠错 | 不自动解关联、转移历史内容或删除用户；当前工具没有覆盖/删除映射命令 |

离线备份恢复用于证明可恢复性和调查，不等于可以将备份直接接回服务。即使没有新增业务数据，备份仍可能含已撤销 Token 和旧密码状态；恢复到新实例后也须重新执行目标会话/证明撤销、应用有效安全变更，再核对新旧期间差异。涉及其他产品时，禁止用全库恢复替代 Work/Club 的范围化回退。

Club 结构回退不执行把邮箱重新改成 NOT NULL 的破坏性降级；新增 NULL 邮箱用户和映射必须保留。恢复旧代码前须确认其可处理当前结构，并继续保留 CLUB-09 对旧写入口和 Cookie 的拒绝；不能直接恢复旧 Better Auth 入口。不能满足则保持维护并向前修复。本轮没有承诺“所有新增登录方式都能在旧版本登录”。

## 7 后续次序与待确认项

WORK-09 / CLUB-09 已在隔离 Home、Club D1 与同一真实 Auth 中完成旧入口、导航、重启恢复及切换回退验证，记录见开发任务第 25 节及 Club 的 `docs/ACCOUNT-CUTOVER.md`。下一步由 AUTH-12 汇总交付矩阵，无需等待真实外部服务凭证。

实际迁移前按以下优先级补充 D-09，当前均未对真实数据执行：

1. **实际部署与数据来源：** 是否存在旧 Java/MySQL、Auth/Club 实际版本和迁移日志、Work personal 是否用过；取得明确授权后再盘点只读副本。
2. **账号可接续性：** 密码格式、未验证邮箱的补验证方案、Google/Apple/GitHub 稳定身份与应用配置、同邮箱冲突的独立归属证据。建议证据不足保持待处理，不自动合并。
3. **切换完整范围：** Work Web/桌面及 Club 全部旧 Client、Cookie/SecretStore/回调位置、其他产品共享情况、停写窗口与回退负责人。建议独立新 Client、一次审核完整清单。
4. **旧 TEAM 纳管：** 所有者和成员清单、VIEWER 的去向、哪些应保持旧空间、哪些由平台纳管。建议默认保留，逐项审核，不自动授予新角色或席位。
5. **真实演练放行：** 账号归属覆盖与待处理用户方案、备份恢复结果、产品收口证据、后续写入兼容性。审核后另做受控迁移任务；本轮工具不直接对线上执行。
