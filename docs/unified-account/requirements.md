# Molis 统一账号 租户与订阅席位需求

状态：2026-11-05，首期规则及开发安排已确认，三仓库实现与隔离证据已由 AUTH-12 汇总。当前[验收矩阵](acceptance-matrix.md)覆盖 42 项要求，其中 39 项在注明范围隔离通过、3 项部分完成；缺口和真实环境待办见[交付记录](delivery.md)。本期交付统一账号、租户成员、订阅席位管理和权益判断服务；具体付费业务、支付及共享后续实施。登录在产品内完成，旧账号与数据按保留处理。

本需求覆盖 `auth`、`molis-work` 和 `molis-club`。Auth 是统一用户和组织事实的来源；商业授权已在 Auth 仓库内作为独立领域实现；Work 与 Club 保留各自界面并消费同一合同。实现及验证状态以交付矩阵为准，不表示已部署。

- 分阶段交付、依赖及退出条件：[实施计划](implementation-plan.md)。
- 请求响应、权限、状态与适配边界：[接口合同](api-contracts.md)；三个仓库的任务、依赖与验收：[开发任务](development-tasks.md)。
- 当前已有 Web 协议：[登录接入说明](../login-integration.md)。该说明描述现状，不代表本需求中的产品内认证、手机登录或产品级退出已经实现。
- 需求和确认记录以本文件为共同来源；实施计划引用需求，不维护第二套产品规则。

## 1 已确认决定

以下决定均来自 2026-11-04 的需求讨论。标为建议或待确认的内容见后文，不纳入本表。

| 决定 | 已确认内容 |
| --- | --- |
| C-01 | Work 与 Club 共用 Auth 的同一套账号；在一端注册的账号可用于另一端。 |
| C-02 | 首期登录方式包括邮箱密码、+86 手机验证码、Google 和 GitHub。 |
| C-03 | 两端各自显示注册和登录表单；邮箱、手机流程在原产品内直接完成，不再要求跳到 Auth 页面确认一次。真实第三方认证进入官方授权页面，开发联调可按 C-37 模拟。 |
| C-04 | 个人资料包括昵称、头像，以及手机、邮箱、Google、GitHub 的绑定管理；多种登录方式关联同一个用户。 |
| C-05 | Work 未登录时仍可使用本地功能，云端功能需登录；不因接入账号而把现有 Home 自动改为云端或租户数据。 |
| C-06 | 一个用户可以加入多个租户，并保留不自动共享的个人空间。 |
| C-07 | 租户拥有的内容在租户成员间共享；成员享有租户的共享内容访问权限。租户管理操作按 C-15 的角色分工提供。 |
| C-08 | 个人购买的权益称为个人订阅；权益归本人，可在个人空间和本人加入的各租户使用。 |
| C-09 | 租户订阅可包含多个不同类型的席位；席位类型决定对应的功能开放。 |
| C-10 | 租户将成员席位分配给本租户人员；它仅在购买方租户内生效，可以释放、回收并换绑给其他成员。 |
| C-11 | 租户正常启用时，没有任何有效订阅或席位的成员仍可查看、下载租户已有共享内容；付费功能需对应权益。 |
| C-12 | 默认退出当前产品，另提供退出全部设备；具体会话、产品和设备范围按 C-33。 |
| C-13 | 首期交付统一账号、租户成员、订阅席位管理和权益校验；具体付费业务接入按 C-26，真实支付、业务数据共享后续实施。 |
| C-14 | 旧账号和数据按保留处理，不自动合并同邮箱账号；旧登录状态的切换按 C-35。 |
| C-15 | 租户采用所有者、管理员、成员三级角色。所有者拥有全部租户管理权限，并负责管理员任命与所有权转让；管理员管理普通成员、租户资料和席位分配/回收；成员使用获授权功能。管理角色本身不自动获得付费功能。 |
| C-16 | 租户仅由平台管理人员创建，再指定用户为租户所有者。普通注册用户不可自行创建租户；平台的创建权限与租户内所有者、管理员的管理权限分开。 |
| C-17 | 租户所有者或管理员通过邮箱、手机号或已有 Molis 账号发出定向邀请；受邀者登录后确认加入，未注册者先完成注册。 |
| C-18 | 成员和管理员可以自行退出租户；所有者须先将所有权转给本租户的一名现有成员，待对方确认接收且交接生效后才可退出，租户始终保有一名所有者。 |
| C-19 | 租户停用和恢复仅由平台管理人员操作；租户所有者有需要时联系平台。租户管理角色本身不包含这两项平台权限。 |
| C-20 | 租户停用后保留成员、订阅和席位等记录，成员不能使用该租户，包括后续共享内容的查看、下载；个人账号和其他租户不受影响。恢复后按届时有效的成员和权益重新开放，首期不提供租户永久删除。停用期间订阅计时按 C-31 处理。 |
| C-21 | 手机号验证码验证成功后，已绑定账号的手机号直接登录；未绑定任何账号的手机号自动创建统一账号并登录，页面事先提示“未注册手机号验证后将自动注册”。已有邮箱或第三方账号的用户可先登录再绑定手机号，以使用同一账号。 |
| C-22 | 新用户使用邮箱密码注册时，先验证邮箱，通过后完成注册并登录；忘记密码可通过已验证邮箱完成重设。旧账号是否补验证及如何切换按 D-09 的迁移方案处理。 |
| C-23 | 登录方式由用户自助管理。绑定、换绑或解绑前，须通过当前账号任一仍可用的登录方式再次验证身份；绑定或换绑还须验证新方式。新方式已被另一账号占用时拒绝绑定，不自动合并；解绑后至少保留一种可用登录方式。 |
| C-24 | 所有已绑定登录方式均不可用时，首期不提供人工账号恢复，用户需先找回原登录方式。通过已验证邮箱重设密码的能力仍按 C-22 提供。 |
| C-25 | 在本人所属且正常启用的租户内，个人订阅与当前租户分配的有效席位按功能取并集；某个来源失效后按其他仍有效的来源保留功能。此规则仅涉及功能开放范围，用量额度叠加另行确定。 |
| C-26 | 首期交付真实权益服务和两端订阅、席位管理，后台根据实际数据判断用户在当前范围是否拥有某项功能权益；具体业务功能的收费规则和入口拦截后续接入，正式套餐功能清单随业务接入确定。 |
| C-27 | 首期个人订阅和租户订阅由平台管理人员统一开通和变更，设置套餐、有效期及租户席位数量，并记录操作。个人用户查看自己的订阅；租户所有者和管理员管理已有席位的分配与回收。 |
| C-28 | 首期订阅均设置明确的开始、到期时间，由平台手动续期。到期后权益计算不再计入该订阅，账号、租户、成员和席位分配记录保留，其他有效权益来源不受影响。 |
| C-29 | 对原租户订阅续期时，席位类型和数量未变则沿用保留的当前分配；租户正常启用、成员资格有效时，续期生效后恢复对应权益。已回收、换绑或因离开租户而结束的旧分配不恢复。 |
| C-30 | 同一租户订阅按席位类型分别调整数量，增加数量不改变有效期；减少后的数量不得低于当前保留的分配数，包括订阅到期后保留的当前分配。超额分配须先由租户管理者明确回收，再由平台减量，不自动挑选成员回收。已结束的历史分配不占库存。 |
| C-31 | 单份订阅停用期间继续计时；租户停用时，其租户订阅也继续计时，均不自动顺延到期日。恢复后按原有效期判断，确需延期由平台调整并记录原因。租户停用不改变成员个人订阅的期限。 |
| C-32 | 平台更换套餐或席位类型时，有效期不自动改变；个人订阅按新套餐计算权益，租户中未变类型的当前分配沿用。要删除或更换的席位类型，先由租户管理者回收受影响分配，再由平台调整，之后明确重新分配，不自动替成员换类型。 |
| C-33 | 普通“退出登录”只结束当前产品的这次登录，其他设备或浏览器中的独立登录、另一产品均不受影响；共用同一次登录的页面会一起退出。另提供“退出所有 Molis 产品的全部设备”，结束该账号在两端的所有登录。 |
| C-34 | 两端默认记住登录，关闭浏览器或应用后重开可自动恢复；每个产品的每次登录独立计时，连续 30 天未主动使用，或本次登录满 90 天时，需重新登录。后台刷新、轮询和自动任务不延长期限；Work 已有本地功能仍可用。 |
| C-35 | Work、Club 切换统一账号方案时，不沿用各自旧登录状态，已有用户需重新登录一次，账号、资料和内容保留。原密码及第三方登录如何接续，待存量盘点后确定；其他产品的 Auth 会话不受影响。 |
| C-36 | 短信和邮件服务尚未准备；先预留真实供应商接入接口，使用 mock 推进开发和联调，实际发送在服务接入后补齐。 |
| C-37 | Google、GitHub 的 OAuth 应用尚未准备；先完成适配接口和模拟联调，应用配置好后再补官方授权页的真实登录验证。 |
| C-38 | Auth 和 Club 的正式域名尚未确定，先使用本地或隔离测试地址开发；在真实短信、邮件和第三方登录联调前，落实正式域名及对应回调配置。Work 的本机入口继续使用本地地址。 |
| C-39 | 已登录改密码保留当前这次登录，撤销其他所有产品和设备的登录；通过邮箱找回并重设密码时，撤销该账号全部登录，再重新登录。该规则与普通退出范围分开。 |
| C-40 | 所有权交接完成后，原所有者变为普通成员，已有席位保持原分配；新所有者如有需要，可再将其设为管理员。 |

## 2 术语与事实归属

| 概念 | 定义 | 建议的唯一事实 owner |
| --- | --- | --- |
| 用户 | 跨产品稳定的人，标识为 Auth userId；手机号和邮箱不是用户主键 | Auth 身份领域 |
| 登录方式 | 用户证明身份的方式，包括密码、已验证手机号、第三方身份 | Auth 身份领域 |
| 个人资料 | 用户选择的昵称和头像；联系方式及其验证状态单独表达 | Auth 账号领域 |
| 租户 | 组织成员和组织内容的边界，不等于某个客户端或应用 | Auth 组织领域 |
| 成员关系 | 某个用户当前属于某个租户，以及对应管理角色 | Auth 组织领域 |
| 个人空间 | 用户私人内容的范围，不因加入租户自动公开 | 业务内容 owner；Auth 仅持有相应身份和组织信息 |
| 个人订阅 | 用户购买或经授权开通的套餐及有效期，权益直接归本人 | 商业授权领域 |
| 租户订阅 | 租户获得的套餐、席位类型、数量及有效期 | 商业授权领域 |
| 成员席位 | 租户订阅下可分配给一个成员的功能使用名额 | 商业授权领域 |
| 权益 | 当前用户在当前范围对某项功能的有效使用资格，是订阅和分配状态的计算结果 | 商业授权领域 |
| 业务内容 | 项目、文档、Goal、附件等实际数据，以及个人或租户归属 | 各业务服务或插件 |

订阅回答“获得什么、有效多久”；席位回答“组织将使用名额分配给谁”。个人订阅不在界面中称作个人席位，也不要求用户给自己分配名额。

现有 Auth `auth_application` 表示 Work、Club 等应用；`auth_grant` 表示登录授权会话。两者都不能被重用为订阅或商业席位表。Auth 的 `PERSONAL/TEAM space` 可作为组织模型基础，但与 Work 本地 Home、保留身份的个人项目分区及 personal 分支的存储空间不是同一份事实，实施时须明确映射。

## 3 首期范围与后续范围

### 3.1 首期交付

Work 与 Club 作为同一账号体系的两个入口，各自在产品内提供下列账号、租户成员、订阅及席位管理页面。页面样式和导航可按产品调整，支持的操作按同一套权限规则提供。

1. 两个产品各自的注册、登录、退出及账号状态；四种登录方式使用同一用户模型。
2. 昵称、头像、登录方式绑定与管理，及避免现有 Club 改密能力退化所需的中央账号接口。新邮箱注册验证及密码找回按 C-22，登录方式管理按 C-23，账号恢复范围按 C-24。
3. 租户列表、创建、停用、恢复和切换、成员列表、邀请或加入、退出或移除，以及管理角色。角色及租户生命周期按 C-15 至 C-20 实施。
4. 个人订阅、租户订阅、席位库存、分配、回收、换绑、有效期和历史记录；首期开通及变更按 C-27 由平台管理人员执行，生命周期规则按 C-28 至 C-32 处理。
5. 统一权益查询与服务端判定，依据实际订阅、席位分配、成员关系和租户状态，对功能标识返回允许或拒绝；两端通过正式接口读取结果。账号、租户、订阅和席位管理操作的身份及权限校验同属首期。
6. 旧账号与数据盘点、映射、迁移演练及可回退的产品切换方案；实际存量维护须按各仓库发布和数据维护约定另行执行。

短信与邮件发送按 C-36、Google/GitHub 提供方按 C-37 先使用 mock，开发地址按 C-38 使用本地或隔离测试环境，不阻塞账号、租户和商业管理的开发联调；mock 仅用于隔离开发/测试环境，真实发送和官方授权作为外部服务接入后的验证项单独记录。

### 3.2 后续实施

- 真实付款、支付回调、自动扣费、发票、退款及升级补差价。
- 正式套餐的业务功能清单与收费规则，以及具体业务入口的权益拦截；涉及的离线付费许可、执行中撤权和用量额度另行确定。
- 租户业务内容的云存储、跨设备同步、多人编辑和共享内容访问入口。
- 将 Work 本地内容发布或迁入租户的交互与存储机制。
- 账号自动合并、公开分享、复杂资源级 ACL，以及尚未定义的商业用量计费，不作为首期默认附带能力。

首期的租户成员和权益管理不构成“租户数据共享已经实现”。C-07、C-11 是后续共享功能必须遵循的规则；首期通过合同与隔离资源夹具验证该边界，实际内容共享验收留到后续。租户切换只改变身份与管理上下文，不得在尚无共享实现时把本地 Home 暴露给其他成员。

## 4 账号与登录流程

### 4.1 产品内直接完成

邮箱和手机流程为：产品表单 → 产品会话适配层与 Auth → 原产品登录成功。Auth 不再插入一次用户必须点击的账号确认页。错误、验证码过期、重试和注册状态均在原产品中反馈。

- Club 建议由服务端持有令牌和刷新状态，浏览器只持产品自己的 HttpOnly 会话标识。
- Work 建议由本机 Host 持有令牌和 PKCE 等临时状态；桌面凭据使用现有安全存储。登录页面仅在提交认证时短暂处理用户输入的密码，不持久保存，也不取得原始账号令牌；插件、Agent 与 MCP 不取得账号凭据。
- Google、GitHub 按钮在产品中展示，真实接入时身份验证在提供方官方页面完成；Work 桌面使用系统浏览器，完成后回原产品。开发阶段按 C-37 使用受控模拟提供方，仍验证从产品发起、回调及返回产品的完整链路。
- 注册与登录复用 Auth 的用户、凭据、会话、审计机制，不在两个产品分别新建密码或验证码校验系统。

现有外部密码表单仍跳转 `/complete`，注册、确认和第三方绑定有 Auth 同源约束。本期要新增明确的产品内认证合同与客户端会话绑定，不得通过伪造 Origin、代理 Auth 浏览器 Cookie 或删去旧校验来绕过现有协议。新合同要验证客户端、应用、一次性事务与当前发起方的关联，处理重放、串号、取消、超时和并发完成。

按 C-38 分环境配置 Auth 地址、Club 来源和回调，并登记客户端与允许的精确回调；开发模拟也不接受请求方任意指定来源或回调。Work 继续遵循本机入口及原生回跳的约束，不为本机 Host 引入公网域名要求。正式域名和对应提供方配置在真实外部服务联调前落实。

### 4.2 统一用户与登录方式

- 统一身份以 `issuer + userId` 表达；业务持久关联使用稳定标识，不以邮箱、手机号或昵称作主键。
- 手机账号和没有邮箱的 GitHub 账号均为正常用户；不得生成占位邮箱满足旧表约束。
- 第三方身份以提供方的稳定身份标识关联；取得第三方账号不等于自动证明同邮箱旧 Molis 账号归本人。
- 按 C-37 提供 Google/GitHub 适配接口及受控模拟提供方，模拟测试身份与成功、拒绝、取消等响应；认证事务、state、回调与发起方绑定、一次性消费和账号关联仍执行实际逻辑，不接受页面自报身份直接建号或登录。模拟身份仅用于隔离测试数据，正式环境拒绝启用模拟提供方，真实配置缺失时不自动回退 mock。
- 登录方式的绑定、换绑与解绑按 C-23 自助完成，通过当前账号任一仍可用的方式再次验证身份，绑定或换绑还须证明新方式由本人控制；已关联另一用户的方式不得自动转移。重复账号合并不属于普通绑定。
- 解绑至少保留一种实际可用的登录方式；旧手机号等单一方式遗失时，可用其他已绑定方式验证后换绑。全部方式都不可用时按 C-24 先找回原登录方式，首期不提供人工账号恢复。
- 改密与邮箱找回后的撤销范围按 C-39。密码变更与会话撤销原子完成，不能由客户端指定任意保留会话；改密保留的当前登录继续受原有 30/90 天期限约束，其他会话的迟到刷新不得恢复登录。
- +86 验证码按登录、注册、绑定或换绑等用途与事务绑定，具备有效期、尝试次数、重发和发送频率限制；发送与消费的并发结果必须确定。
- 按 C-36 在 Auth 内提供短信、邮件发送适配接口，先实现 mock 投递，再接真实供应商。mock 只替换外部发送，验证码或邮件验证凭据的生成、用途绑定、有效期、尝试限制和一次性消费仍执行同一套真实逻辑，不以固定万能验证码或直接返回认证成功代替。测试投递通过隔离测试设施获取，原始验证码和邮件验证链接不写入普通业务日志或正常产品接口响应；验证后的短期操作证明仅交受保护的 BFF/Host，不进入页面。正式环境拒绝启用 mock。
- 手机号不作为默认公开昵称。联系方式是否存在、是否已验证、是否可用于登录应分别表达。

### 4.3 会话与退出

统一账号不意味着两产品必须共享同一个浏览器 Cookie，也不承诺进入另一产品自动登录。首期各产品会话独立管理，退出范围按 C-33，登录保持与自动恢复按 C-34。

两端默认记住登录，在凭据仍存在且服务端会话有效时，关闭后重开自动恢复。每个产品的每次登录分别记录登录时间和最近主动使用时间，按“闲置 30 天”和“本次登录最长 90 天”中较早的期限失效；主动使用只能更新闲置时间，不能推迟本次登录的 90 天上限。共用同次登录的页面共同计时，另一产品或其他独立登录的活动不能替本次登录保活。

用户主动打开使用、查询或编辑等行为可作为活跃信号；后台身份恢复、令牌刷新、轮询、同步及自动任务不计入主动使用。活动更新和期限判定由服务端按统一合同处理，客户端不能通过本地时间或旧缓存延长登录。过期后重新登录，Work 已有本地能力不受影响；敏感账号操作仍按 C-23 再次验证身份。

普通退出必须撤销当前产品这次登录的凭据并清理本端状态，不影响同产品其他独立登录或另一产品会话；不能仅清界面状态。共用同次登录的页面一起退出，包括 Club 同一浏览器会话的多个标签页，以及 Work 连接同一本机 Host、共用其账号状态的入口；不能仅凭物理设备或浏览器窗口划分会话。

“退出所有 Molis 产品的全部设备”撤销该账号在所有产品、设备上的登录。现有 Auth 根会话退出端点不能直接替代这两种范围，需要分别实现当前产品登录会话级与账号全局撤销。撤销时不得出现稍后完成的刷新或登录重新恢复旧会话。

Work 离线时退出应清除本端凭据并准确区分远端撤销是否成功。离线身份缓存只能表达曾登录的身份，不能证明订阅或成员资格仍然有效；首期权益判断由服务端执行，后续业务的离线许可规则见 D-06。

## 5 租户成员与内容边界

用户可在个人上下文和多个租户上下文之间切换。进入租户、查看租户管理数据或执行租户操作时，服务端重新确认租户启用状态与当前成员关系；前端传入的 tenantId 只是请求目标，不是访问证明。停用与恢复按 C-20 处理，个人订阅不能绕过租户停用限制；该限制不撤销用户在个人空间或其他正常租户中的独立权益。

共享内容访问资格、管理角色和商业功能许可分别判断：

1. 成员关系决定用户是否可访问该租户共享内容。
2. 租户管理角色决定谁可以管理成员、租户资料及席位分配与回收，具体角色矩阵见 D-02；订阅开通与变更按 C-27 属于平台管理权限。
3. 订阅或成员席位决定该用户能否使用对应付费功能，不能授予非成员访问租户数据的权利。

离开或被移出租户不会删除该用户的全局账号或个人订阅；此后服务端必须拒绝该租户访问。已产生且归属租户的内容保留在租户，不随席位回收或成员离开转移给个人。

建议成员移除与组织席位释放由服务端统一编排，使用同库原子操作或可靠事件与幂等消费；不能依赖 Club 和 Work 各自调用一次来完成。按 C-29，因离开租户而结束的旧分配不恢复；再次加入后须由租户管理者重新分配，不能因历史记录存在而自动恢复旧席位权益。

Auth 当前邀请仅支持已有账号的邮箱，首期按 C-17 补充手机号、已有 Molis 账号及邀请未注册者的路径；无邮箱第三方用户可通过已有 Molis 账号接受邀请。邀请发出后不立即建立成员关系，须由目标身份登录并确认加入。当前 OWNER 不可退出且没有所有权转让路由，首期按 C-18 增加交接及交接后的退出能力；交接生效时核对接收人仍是当前成员，并保持所有者唯一。

交接完成后原所有者按 C-40 变为 MEMBER，交接本身不回收其已有席位；其随后离开租户时仍按离开规则释放分配。

Work 旧团队协作草案采用显式项目授权。本期不改其业务存储或运行行为；后续共享方案须以本次确认的“租户归属内容成员共享、个人内容不自动共享”为输入，明确哪些内容进入租户，并同步修订冲突的旧草案，不保留两套相互矛盾的访问承诺。

## 6 订阅 席位与权益

### 6.1 领域模型建议

| 对象 | 最少需要表达的信息 |
| --- | --- |
| 套餐及版本 | 稳定功能标识、适用产品、套餐版本；首期建设配置模型，正式业务功能清单随 D-01 后续接入确定 |
| 个人订阅 | 所属用户、套餐版本、开通来源、起止时间、状态及审计依据 |
| 租户订阅 | 所属租户、套餐版本、席位类型与数量、起止时间、状态及开通依据 |
| 席位或席位库存 | 所属订阅和租户、类型、有效期、可分配容量；独立席位记录或数量池是实现选择 |
| 席位分配 | 成员、所属租户、分配来源、开始和结束时间、操作者、原因及历史 |
| 权益结果 | 用户、请求范围、功能、允许或拒绝、来源、版本和有效期限 |

购买记录、订阅生效与席位分配不是同一个状态。未分配的组织库存不授予任何成员使用权；成员不能通过修改请求把其他人的席位用于自己。首期不接支付，界面不得让“购买成功”替代尚未接通的支付确认。

### 6.2 功能判定

已确认的适用范围：个人订阅适用于本人及本人当前加入的租户；成员席位只适用于购买方租户。租户上下文还须满足租户正常启用、当前成员关系有效；内容访问由内容归属进一步约束。

按 C-25 已确认的功能计算规则：

```text
个人上下文的有效功能 = 本人有效个人订阅包含的功能
租户上下文的有效功能 = 本人有效个人订阅功能 ∪ 当前租户分配给本人的有效席位功能
```

同一功能存在多份有效授权时，回收其中一份不应误伤其余有效授权。未来如引入用量额度，额度叠加不得从上述功能并集自动推导。

首期依据持久化的订阅和分配记录执行上述判定，两端展示同一服务的结果。下表描述权益的适用规则；具体业务功能调用判定接口并执行限制，按 C-26 后续接入。

| 场景 | 预期边界 |
| --- | --- |
| 有个人订阅，没有组织席位 | 在个人空间及本人加入的租户内使用该订阅包含的功能 |
| 只有甲租户分配的席位 | 仅在甲租户使用该席位功能；不扩展到个人空间或乙租户 |
| 没有有效订阅或席位 | 仍可查看、下载本人所属且正常启用的租户已有共享内容；对应付费功能拒绝 |
| 租户回收席位，个人订阅仍有效 | 按剩余个人授权判断功能，个人订阅不被撤销 |
| 离开租户，个人订阅仍有效 | 个人订阅继续有效，但不能访问离开的租户 |
| 席位到期或被换绑 | 不删除已有内容；旧使用者不能继续依赖旧分配使用付费功能 |

### 6.3 生命周期与执行约束

- 按 C-30 在同一订阅内逐席位类型校验容量，当前保留的分配不得超过配置数量，包括订阅到期后保留的当前分配；已结束的历史分配不占库存。同一席位不能同时绑定多人，并发分配、回收、换绑和减量需原子校验、幂等处理并留下历史。
- 增加数量不改变有效期，也不使已到期订阅恢复权益；减量前先由租户管理者明确回收超额分配，再由平台调整数量，不自动挑选成员回收。
- 回收与换绑不延长订阅有效期，也不把旧使用者的私人内容授予新使用者。
- 订阅期限和到期按 C-28 处理，原订阅同类型、同数量续期按 C-29 沿用当前分配，不把新订阅自动关联到历史分配。到期、停用、成员变化和席位变化须使对应权益版本失效；首期不执行支付退款。
- 停用计时按 C-31 处理：单份订阅停用时该来源不计入权益，其他有效来源仍可用；租户停用时拒绝该租户访问。两种停用均不自动顺延相关订阅的到期日，恢复时复核原有效期及当前状态，已到期的订阅不会仅因恢复而重新生效。租户停用不改变成员个人订阅的期限，个人订阅也不能绕过该租户停用；平台单独延期须记录原因。
- 套餐或席位类型变更按 C-32 处理，不自动改变有效期；个人订阅按新套餐重新计算权益。租户中未变类型沿用当前分配，数量调整同时遵守 C-30；删除或更换类型前须已回收该类型的当前分配，包括到期后保留的分配。平台变更完成后由租户管理者明确重新分配，保留回收与变更历史，不自动把旧分配转为新类型。
- 权益入口不得相信页面传来的套餐、角色、userId 或“已付款”标记。业务端核对令牌所属应用和客户端，操作者来自可信会话。
- 后续 Work 接入具体付费业务时，将功能限制接入现有动作发现、受理及 `beforeEffect` 写入前复核；页面、工作流、Agent、MCP 和插件调用使用同一规则。
- 功能判断不能替代业务对象归属校验。后续列表、搜索、附件与同步均须由资源 owner 核对租户。
- 后续业务执行接入时，同步事务内不临时等待 Auth 网络请求；需要权益快照时记录范围、期限和版本，离线付费许可及执行中撤权按 D-06 确定。首期管理和权益接口仍须处理状态变更与缓存失效。
- 首期使用隔离环境中的套餐、功能项及实际订阅/分配记录验证真实服务与两端调用，不以固定界面结果替代判定。正式业务功能清单不阻塞本期；既有未登录本地能力按 C-05 保留。

## 8 旧账号与数据保留

保留包括稳定业务归属、已有账号的可恢复使用路径和必要历史；旧会话切换按 C-35，账号映射与凭据接续仍需存量盘点及验证，不把它们合成一个“迁移完成”标记。

建议的切换原则：

1. 先在获准环境盘点两套用户、登录方式、密码格式、业务外键、重复邮箱和旧会话；此需求不授权读取或修改真实用户数据。
2. 保留 Club 本地业务 user.id 和 notes.user_id，建立唯一且可审计的旧用户到 Auth 用户映射；业务关联不靠改邮箱或重写所有历史作者完成。
3. 同邮箱未验证时不自动合并；用户需通过旧凭据验证、已有可靠关联或明确受控认领路径完成归属证明，不能默认要求所有用户重新注册。
4. Club 用户邮箱必填与唯一约束须支持新无邮箱账号；历史邮箱数据保留，其可信程度不因迁移被升级。联系表中填写的邮箱不是账号归属证明。
5. Auth 的[密码校验](../../worker/rust/src/password_kdf.rs)使用固定版本的 PBKDF2 格式；Club 使用锁定版本 Better Auth 的默认密码实现，仍需核对依赖源码、实际部署版本和存量格式，再设计凭据接续并做隔离验证，不假设能直接复制密码哈希。仅在盘点证明不能保留原密码登录体验时，再确认是否接受验证身份后重设密码；算法和映射实现由工程调查确定。
6. 按 C-35，在各产品切换时停止接受其旧登录状态，用户重新登录后建立符合 C-33、C-34 的新会话；不复制旧 session 或把旧缓存直接升级为新会话。范围仅限 Work、Club，不能通过 Auth 全局撤销影响其他产品。Work 主线目前没有接通账号登录，personal 分支是否存在实际使用的旧会话须盘点，不预设已有存量。
7. 在脱敏副本上验证幂等、冲突、失败恢复、映射覆盖和外键完整性；切换应有备份、停止条件及经过演练的回退路径。回退不得恢复已撤销权限或丢失切换后新增数据。
8. Work 现有本地身份和 Home 业务记录不因登录、换账号或退出被批量重写、删除或上传。涉及真实 Home 及数据格式的后续维护，遵循 Work 现有发布和合同变更规则。
