## 1. 本轮范围与实施原则

首期交付统一账号、个人资料与登录方式绑定、租户成员、订阅与席位管理，以及真实服务端权益判定和两端调用。具体付费业务入口拦截按 C-26 后续接入。登录方式包括邮箱密码、`+86` 手机验证码、Google、GitHub。邮箱和短信认证在产品自己的界面内完成；真实 Google、GitHub 登录进入供应商官方授权页面。

短信和邮件按 C-36、Google/GitHub 按 C-37 先预留适配接口、使用 mock 完成开发联调，开发地址按 C-38 使用本地或隔离测试环境，正式域名及回调在真实外部服务联调前落实。mock 仅替换外部投递或提供方响应，账号验证及成员、订阅、席位、权益服务仍使用实际实现和隔离测试数据；外部服务准备好后再接真实发送和官方授权并补验。

个人订阅可用于本人加入的各租户；租户订阅购买成员席位，租户分配的席位仅适用于买方租户。用户可加入多个租户，并保留独立个人空间。租户正常启用时，没有订阅或席位的成员可以查看、下载共享内容；这是一条后续内容服务必须遵守的规则，不代表首期已经建设共享存储与同步。

具体付费业务接入、真实支付和业务数据共享另列后续项目。首期由平台管理人员按 C-27 开通和变更订阅，客户端不能自行开通权益。旧账号、资料和业务数据必须保留，会话切换按 C-35 重新登录；账号映射与凭据接续在 D-09 盘点后确定。

实施遵循以下边界：

- Auth 拥有统一用户、认证凭据、个人资料、租户、成员与管理角色的事实。两产品可以有自己的表单和缓存，但不再各自拥有一套账号、密码或绑定关系。
- 商业授权独立成模块，拥有订阅、席位库存、分配记录与权益事实。首期已在 Auth 仓库同 D1 实现，运行与领域边界见交付说明；没有据此部署真实环境。订单和支付记录以后归支付领域，不混进用户登录会话。
- Club 与 Work 保有各自的业务数据及本地会话。需要资源授权时，由资源所属服务确定真实租户，不能直接相信客户端提交的租户 ID。
- Work 未登录仍可使用已约定的本地能力；新增云账号或商业授权故障不能顺带阻断这些能力。付费本地业务、离线许可与执行中撤权留到 D-06 后续接入时确定。
- 复用现有协议和安全机制时以当前代码为准。不得通过伪造 `Origin`、关闭来源校验或复制 Auth Cookie 来绕过现有交接流程。
- 不把身份缓存视作成员资格或付费凭证；不把 `auth_grant` 登录授权会话改作商业席位账本。

本文记录整体计划，各任务的已执行验证以开发任务实施记录为准；未列出证据的测试、迁移与上线操作仍待实施。真实数据维护、推送和部署遵守各仓库当时的开发规则及所需授权。

## 3. P0：模型、协议与存量盘点

### 输出与跨仓库任务

- **Auth**：画清用户、登录身份、个人空间、租户成员、管理角色、个人订阅、租户订阅、成员席位之间的关系；区分成员数据访问、管理操作和商业功能许可。
- **Auth**：制定产品内认证合同。分别描述已登记 Web 客户端与桌面公共客户端的创建事务、验证凭据、完成认证、令牌交付、续期、退出、取消和错误恢复；新流程必须具有客户端、事务、请求方和回调绑定。
- **Auth**：明确 `/users/me` 的应用与客户端校验责任、无邮箱用户的返回形状、资料及绑定接口、租户成员失效合同、权益输入输出和版本语义。
- **Club**：盘点旧用户、密码格式、业务主键引用、资料、会话与已启用登录方式。制定旧业务用户到统一 Auth userId 的明确映射，记录碰撞及待处理项；会话切换按 C-35，不以保留旧登录状态为前提。旧密码、第三方身份接续和必要的补验证步骤根据盘点结果提出方案。
- **Work**：盘点 main 的本地身份、SecretStore、浏览器/桌面入口和 personal 分支可复用代码；仅选取账号接入部分，不把 personal 的同步、发布或云存储一起合入。
- **共同**：制作不含凭据的环境与回调清单、数据保留清单、合同调用图、风险清单及未决项台账。按 C-38 先登记本地/隔离测试的 Auth 地址、产品来源、客户端与允许回调；不把现有预览地址视为已选定的正式域名，也不为 Work 本机 Host 要求公网域名。生产盘点若需要访问真实系统，另取得相应权限并限定只读范围。

### 依赖与必要决策

按 D-01 至 D-05、D-07、D-08 已确认的首期规则落实合同，先盘点并确定 D-09 中影响基础合同的部分，存量切换细节在 P4/P5 前闭合。D-10 按 C-36 至 C-38 先使用本地/隔离测试与 mock，真实供应商、OAuth 应用、正式域名和回调列为后续接入准备，不阻塞当前开发。正式业务功能清单及 D-06 的离线付费许可留到业务接入前确定，不阻塞首期权益服务。

### 建议拆分

1. 三仓库现状和存量引用清单。
2. 身份、认证、绑定、退出协议评审。
3. 租户与商业授权模型及事实归属评审。
4. 旧数据映射、测试夹具和切换方案评审。

### 验证证据与退出条件

使用示例和状态表评审以下场景：无邮箱用户；同一人有多个登录方式；两个旧账号同邮箱；个人订阅跨已加入租户；成员席位仅所属租户；成员离开后保留租户内容；启用租户内的无席位成员查看和下载；不同产品退出互不误伤。

退出条件是合同和映射方案可供实现、事实只有一个 owner、阻塞决策有明确结论，且任何不能自动映射的存量均有处理方案。此阶段产出是设计证据，不宣称产品测试通过。

## 4. P1：Auth 产品内认证与个人账号

### 输出与跨仓库任务

- **Auth**：实现经评审的产品内邮箱、短信认证协议。明确哪些接口允许已登记产品来源、哪些由 BFF 或 local-host 调用；注册不能继续依靠现有仅 Auth 同源的入口，也不能伪造该来源。
- **Auth**：新增 `+86` 手机身份、验证码发送和验证、用途隔离、错误次数与重发限制、一次性消费及审计。验证后按 C-21 登录已有账号或创建统一账号，两产品提前展示自动注册提示；外部短信投递按 C-36 先 mock。
- **Auth**：为短信和邮件提供可替换的发送接口及 mock 适配器，供应商后续接入时不改变两产品的认证合同。验证码、邮件验证凭据及消费状态由 Auth 管理，mock 只模拟投递及发送失败，不直接授予登录成功。测试投递使用隔离测试设施，正式环境拒绝启用 mock。
- **Auth**：整理 Google 适配接口并新增 GitHub 适配器，复用供应商状态绑定与账户关联编排，分别实现供应商可信身份验证。按 C-37 先用受控模拟提供方联调，应用配置完成后补真实授权验证。模拟只替换提供方响应，不绕过认证事务、state、回调绑定与一次性消费；测试身份不得进入真实用户数据。缺少邮箱时允许按已定模型创建账号，不使用占位邮箱。
- **Auth**：统一昵称、头像及手机、邮箱、Google/GitHub 登录方式管理。按 C-23 提供用户自助绑定、换绑和解绑，使用任一仍可用方式再次验证当前账号；绑定或换绑验证新方式，拒绝占用冲突与自动合并，解绑后至少保留一种实际可用方式。
- **Auth**：按 C-22 实现新邮箱注册验证及已验证邮箱的密码找回，并保留 Club 已有改密码能力；旧账号补验证按 D-09 处理，邮件投递按 C-36 先 mock，真实供应商配置和发送验证后续补齐。全部登录方式不可用时按 C-24 引导找回原方式，首期不建设人工账号恢复入口。
- **Auth**：按 C-33 分别实现当前产品这次登录的撤销和该账号所有 Molis 产品、全部设备的撤销；普通退出不影响其他独立会话，共用会话的页面一起退出。现有根会话撤销不能直接充当这两种操作。
- **Auth**：按 C-39 将改密/找回与会话撤销原子提交：改密只保留可信当前登录，找回重设撤销全部；不接受客户端自选保留会话，不让旧事务或迟到刷新绕过撤销边界。
- **Auth + 两产品**：按 C-34 默认记住登录，定义每个产品每次登录的主动活动更新合同，独立执行闲置 30 天、最长 90 天的期限。后台恢复、刷新、轮询及自动任务不保活，其他独立会话不代为续期；协调服务端会话、刷新凭据与产品 Cookie 的有效期和持久化，不能只修改一个过期常量。过期或撤销后不得自动恢复旧登录。
- **Club / Work**：提供各自调用形状、来源和回调约束的合同夹具；校验用户响应中的应用与客户端归属。产品界面遵循统一合同，不独立编写验证码或绑定业务规则。

### 依赖与建议拆分

依赖 P0 身份与认证合同及 D-05/D-08 已确认规则。外部依赖按 C-36、C-37 先通过 mock 联调，环境与回调按 C-38 登记；真实发送与官方授权部分依赖 D-10 的供应商、OAuth 应用及正式域名配置，不阻塞当前内部流程开发。建议拆成认证交付协议、短信、供应商适配、资料绑定、会话保持与退出五组；共享模型和路由改动由一个集成负责人协调。

### 规划中的验证证据

- 新邮箱验证后在产品内完成注册登录，通过已验证邮箱重设密码；邮箱未验证时不能完成新账号注册，过期或已消费的验证凭据被拒绝，密码错误、重复提交、错误来源、错客户端和事务过期仍被拒绝。
- 手机号验证后复用已有账号或创建新账号，并发首登不重复建号；短信发送失败、重发、错误次数耗尽、旧码失效、用途串用、并发重复消费和手机号绑定冲突。
- mock 发送成功、失败和重试均进入真实验证流程；测试投递可取到本次生成的凭据，固定万能码或跳过验证不能通过。普通业务日志和正常产品响应不暴露验证码/验证链接，验证后的短期证明仅交受保护 BFF/Host；正式环境配置 mock 时被拒绝，未来真实适配器复用同一发送合同用例。
- 按 C-37 用模拟 Google/GitHub 提供方验证成功、拒绝授权、错误 state、缺浏览器绑定、重复回调、身份已占用、无邮箱开户及取消后的旧回调；正式环境拒绝启用或自动回退模拟提供方。真实应用准备好后补官方授权、真实身份响应和两端回跳验证。
- 上传头像清洗、空邮箱资料展示、绑定后两产品显示同一身份、敏感资料不作为公开昵称。
- 旧手机号不可用时可通过其他已绑定方式验证后换绑；当前身份未再次验证、新方式验证失败、方式已被占用及解绑最后一种方式均被拒绝。
- 全部登录方式不可用的帮助动线引导找回原方式，不提供人工账号恢复；已验证邮箱密码找回仍正常可用。
- 续期竞争、响应丢失和退出时在途登录/刷新返回；按 C-33 验证普通退出仅撤销当前产品这次登录，共享该会话的页面一起退出，同产品其他独立登录与另一产品会话仍有效；全局退出撤销两端所有设备会话，旧响应不能恢复已撤销登录。
- 按 C-34 验证闲置 30 天与本次登录 90 天的边界、用户主动使用仅更新闲置期限、后台及其他独立会话不保活；有效凭据跨浏览器、应用或 Host 重启可恢复，已过期或撤销会话拒绝恢复。持续主动使用不能绕过 90 天上限，凭据轮换与 Cookie 更新须支持有效会话恢复且不能超过服务端会话期限。

单元和隔离后端测试应覆盖拒绝本身。按 C-36、C-37 先用 mock 验证协议和两端流程；真实发送及官方 OAuth 授权在外部服务接入后使用指定测试账号与隔离配置补验，分别记录结果，不把模拟身份或 Token 测试当成已完成官方授权验证。

### 退出条件

四种登录方式和资料绑定形成同一统一用户；代表两产品的协议客户端夹具可通过冻结合同完成认证，实际产品界面由 P4 接入并在 P5 验收；退出与续期语义有证据；没有把 service secret 放进浏览器或桌面分发包。外部发送及 Google/GitHub 可按 C-36、C-37 以 mock 完成此阶段的内部流程验收，真实发送与官方授权另记待接入、待验证，不阻塞后续开发。

## 5. P2：租户、成员与管理生命周期

### 输出与跨仓库任务

- **Auth**：实现多租户和独立个人空间的统一查询与选择上下文；管理角色依据 D-02，不能把购买权限或成员席位隐含在角色中。
- **Auth**：完善租户创建、邀请、加入、退出、移除和所有权转让。创建仅允许平台管理人员执行，并指定租户所有者；所有者或管理员通过邮箱、手机号或已有 Molis 账号定向邀请，受邀者登录后确认加入，未注册者先注册。成员和管理员可自行退出，所有者按 C-18 完成交接后退出。
- **Auth**：按 C-19、C-20 实现平台停用与恢复。停用保留记录并拒绝成员使用租户，个人账号和其他租户不受影响；恢复按有效成员和权益判定，首期不提供永久删除。
- **Auth**：定义成员状态版本、变更审计与可靠失效通知；成员离开后身份会话可以继续用于其他租户，但不再获得原租户访问资格。
- **Club / Work**：接入共同的租户列表与切换合同，切换后清理前一个租户的页面状态和缓存；不建立各自可写的成员表。
- **商业模块**：消费成员生命周期合同，为 P3 的离租户席位释放预留同库原子调用或可靠事件接口。

### 依赖与建议拆分

依赖 P0 租户模型和 D-02、D-07。可与 P1 并行实现；最终需使用 P1 的真实统一身份联调。建议拆成租户及个人空间、邀请、成员管理与所有权转让、版本及失效通知四组。

### 规划中的验证证据

- 一个用户加入多个租户并保有个人空间；切换租户不混入前一租户内容或身份上下文。
- 平台管理人员创建租户并指定所有者；创建、停用和恢复均检查对应平台权限，仅有租户所有者或管理员角色不能通过。
- 停用后两端均拒绝租户访问，记录仍保留，个人账号和其他租户不受影响；恢复不重新授予已失效的成员资格或权益。
- 邮箱、手机号及无邮箱账号均可接受定向邀请，未注册者先注册；本人确认前不建立成员关系，过期、撤销、重复接受和错误接收方被拒绝。
- 不具备管理权限的人不能邀请、移除成员或转移所有权；交接须由当前成员本人确认，生效前原所有者不能退出，生效后所有者唯一。
- 按 C-40 验证交接后原所有者为 MEMBER、已有席位保留；新所有者另行授予 ADMIN 时再生效，原所有者随后退出则释放分配。
- 成员离开/被移除后，新的原租户请求被拒绝，但其他租户和个人空间仍可使用。
- 同时移除、重新加入、变更角色时版本和审计一致；旧版本状态不能恢复已撤销成员资格。

### 退出条件

租户成员有唯一事实来源；角色与内容共享规则已分开；手机/无邮箱成员、所有者转让和成员撤销均有验证。真实共享存储尚未建设时，仅验收成员合同与资源归属测试夹具，不宣称共享业务数据已经完成。

## 6. P3：订阅、成员席位与权益校验

### 输出与跨仓库任务

- **商业模块**：建立功能与套餐配置、个人订阅、租户订阅、席位类型、库存、分配历史和有效权益模型；明确购买主体、受益用户、适用租户、有效期和状态。不要复用登录 `auth_grant`。
- **商业模块**：按 C-27、C-28 实现平台管理人员的个人/租户订阅开通、变更及手动续期，校验套餐、明确的起止时间及席位数量并审计。使用正式受控流程，不以开发测试入口代替。
- **商业模块**：原订阅同类型同数量续期按 C-29 沿用当前分配；数量调整按 C-30 分席位类型处理，增量不改有效期，减量须先回收超额分配。单份订阅或租户停用按 C-31 继续计时、不自动顺延，平台单独延期记录原因。
- **商业模块**：套餐或席位类型变更按 C-32 不自动改变有效期；个人订阅按新套餐计算权益，租户未变类型沿用当前分配。删除或更换类型先由租户管理者回收受影响分配，再由平台调整，之后明确重新分配，不自动换类型；与 C-30 的容量校验及分配并发控制保持一致。
- **商业模块**：实现分配、释放、重新分配与到期。租户分配席位只用于该租户；个人订阅用于本人加入的租户。有效功能按 C-25 取并集，正式业务清单及入口拦截按 C-26 后续接入。
- **Auth + 商业模块**：将成员离开与该租户席位释放做成可靠一致的流程。同一数据库可用受控模块调用和事务；若跨服务，需可靠事件、幂等消费和补偿校验，不能只让前端连续调用两个接口。
- **商业模块**：提供版本化权益查询与服务端判定，区分身份无效、租户停用、非成员、订阅无效、席位未分配和功能未包含。制定缓存失效、重新加入、席位再分配及撤权规则。
- **Club / Work**：调用真实权益查询与判定接口；可以缓存展示，但不自行计算或写入订阅事实。账号、租户、订阅和席位管理接口仍执行身份及权限校验；产品业务动作映射留到后续接入。

### 依赖与建议拆分

依赖 P0 商业模型、P2 成员生命周期合同及 D-01 至 D-04 的已定首期规则。建议拆成订阅及开通、席位库存与分配、成员联动回收、权益判定与失效四组。

### 规划中的验证证据

- 个人订阅跨本人已加入租户可用，但不能访问未加入租户的数据。
- 租户席位不能用于其他租户；未分配库存不计入某个用户的权益。
- 库存不足、重复分配、并发分配、错误管理人和向非成员分配被拒绝。
- 同一订阅按席位类型分别校验数量；增量不改变有效期或恢复已到期权益，减量低于当前保留分配数时拒绝，先回收再减量可成功。到期后保留的当前分配计入容量，已结束的历史分配不计入，不自动挑选成员回收。
- 成员离开后组织席位释放，个人订阅保留；重新加入不会自动恢复旧组织分配。
- 个人订阅与当前租户席位按 C-25 取功能并集；一个来源到期或被撤销后，保留其余有效来源提供的功能。
- 生效前和到期后的订阅不计入权益；到期保留账号、租户、成员及分配记录，不使其他有效来源失效。
- 单份订阅停用只移除该权益来源，租户停用拒绝该租户访问；两种停用均不自动顺延相关订阅到期日。停用期间跨过到期日后，恢复不重新激活该订阅权益；租户停用不改变个人订阅期限，平台单独延期可追溯原因。
- 原订阅同类型同数量续期沿用当前分配，但须租户启用且成员有效；已回收、换绑或离租户结束的分配不恢复，新订阅不自动继承旧分配。
- 套餐或类型变更不改变有效期，个人权益按新套餐计算；未变席位类型沿用当前分配，删除或更换类型有当前分配（含到期保留）时拒绝。回收后才可调整，再由租户管理者重新分配；并发分配不能绕过变更前的回收条件，已回收记录不自动映射到新类型。
- 到期、停用、减席位、释放与再分配的并发结果一致，库存不为负，分配历史可追溯。
- 无订阅或席位成员不因商业校验而失去允许的共享内容查看、下载；资源访问仍要求租户正常启用且成员资格有效，个人订阅不能绕过租户停用。
- 在隔离环境配置功能项和套餐，通过实际订阅、分配记录验证接口的允许/拒绝、组合和失效结果；正式业务清单不作为本期前置条件。
- 权益接口异常、断网或缓存过期时显示相应状态，不把旧登录状态或页面缓存当作当前有效的服务端结论。

### 退出条件

平台开通与变更权限及审计已验证；权益可以追溯到有效订阅及分配；成员撤销和席位回收不会相互遗漏；真实服务可对功能标识作出允许/拒绝判定，客户端不能自行授予权益。具体业务执行接入另期验收；本阶段不创建支付订单或声称款项已收取。

## 7. P4：Club 与 Work 并行接入

### Club 输出

- 在产品内提供统一账号的注册/登录、个人资料、绑定、租户和订阅席位界面；真实第三方登录进入官方授权，当前按 C-37 先走模拟提供方的完整回跳链路。
- BFF 持有 Auth 用户令牌，浏览器只持本产品 HttpOnly 会话。按 C-34 持久化有效登录并在浏览器重开后恢复，实现主动活动更新、跨实例刷新协调、会话与权益失效处理，以及应用/客户端归属核对。
- 依 P0 的已确认映射保留旧业务主键及其数据引用，逐步切换认证 owner；昵称、头像和绑定信息以 Auth 为准。按 C-35 停止接受旧 Better Auth 会话并引导重新登录；旧密码及第三方身份接续依 D-09，不要求旧用户重新注册，也不长期保留双账号写入。
- 将商业管理页面作为服务客户端，不在 Club 中新增第二份订阅、席位或成员事实。

### Work 输出

- 在工作台内提供注册/登录、个人资料与绑定、租户成员、个人及租户订阅、席位查看与管理界面，按 Work 的界面规范组织。
- local-host 统一持有账号会话，浏览器和桌面入口通过现有本机安全边界调用；退出按 C-33，共用同一 Host 账号会话的入口一起退出。按 C-34 统一持久化与重启恢复，复用适合的 SecretStore 能力；不沿用 personal 分支 Web 固定 8 小时且仅存内存的限制，也不把离线身份缓存视为有效云会话。
- 选择性复用 personal 分支的账号接入思路和已验证代码，并适配 main 当前合同、错误处理与安全规则；不合入其个人同步、发布或云存储实现。
- 若盘点发现实际使用的 personal 旧登录状态，按 C-35 在切换时停止沿用并引导重新登录，保留账号、资料及 Home 内容；不为此撤销其他产品的 Auth 会话。
- 产品内邮箱/短信表单调用 Auth 的正式产品认证合同；真实第三方登录通过系统浏览器或获准的官方授权入口完成，当前按 C-37 以模拟提供方验证发起与回跳。桌面公共客户端不携带服务凭据。
- 保留未登录本地使用，区分本地身份、云账号、当前租户和商业权益。账号或租户切换不得让新账号读取上一身份受限的云端状态。
- 通过 local-host 接入中央权益查询与判定，展示当前范围的权益；账号和管理请求由服务端核对身份及权限。具体业务动作拦截、离线付费能力按 C-26 后续接入。

### 依赖、拆分与并行方式

P0 冻结所需合同后，两仓库可立即分别开发调用适配器、页面及合同测试；P1–P3 分批具备能力后逐条替换模拟服务并联调。需要成员或权益的页面，不以未评审的临时字段继续推进。

Club 可拆为 BFF 会话、账号页面、租户商业页面、旧数据映射接入；Work 可拆为 local-host 账号服务、桌面/浏览器入口、资料与租户成员界面、订阅席位界面、权益接口接入。共享合同由 Auth 维护，避免各仓库各自解释。

### 规划中的验证证据与退出条件

验证真实两端注册登录、跨产品同一用户、资料与绑定一致、C-33 的当前会话退出隔离及所有产品全部设备退出、C-34 的活动计时与重启恢复、租户切换、无邮箱界面、权益变更，以及 Club 旧内容归属不变。Work 另外验证无登录/断网及登录过期后的本地能力、旧回调唤起、重复登录、进程重启和账号切换隔离；共享同一 Host 会话的入口须反映一致的退出状态。

退出条件是两产品均使用真实中央服务完成链路，没有复制账号、成员或商业事实；外部发送和 Google/GitHub 可按 C-36、C-37 使用 mock，并明确记录这一依赖；存量映射符合 D-09；Work 未混入 personal 同步范围。邮箱/短信登录在产品内直接完成已确认，验收不得出现额外 Auth 账号确认页；具体界面样式在实现时评审。

## 8. P5：端到端验收、迁移演练与灰度

### 输出与跨仓库任务

- 共同维护验收矩阵，将 P1–P4 场景关联到 [需求验收标准](requirements.md#10-验收标准)，记录测试版本、环境、实际结果和未完成项。
- 使用隔离数据库及适当脱敏的存量样本演练账号映射、凭据接续与 C-35 的重新登录切换；核对用户数量、身份唯一性、旧业务数据引用与内容归属，重复执行不能重复建号。验证 Work/Club 旧会话被拒绝且其他产品的 Auth 会话仍有效。
- 为不可自动处理的碰撞建立明确处理清单，不按同邮箱自动接管或丢弃账号。
- 制作部署顺序、数据备份、应用回退和数据恢复方案。区分“回退程序”与“恢复数据库”，防止旧版本无法读取新结构；先在隔离环境演练两者。
- 灰度前记录错误率、登录及刷新失败、短信发送、绑定冲突、成员撤销与权益判定的观察指标；日志只保留必要标识与结果，不记录凭据和完整验证码。

### 建议拆分

1. 跨产品端到端与安全拒绝验收。
2. 存量迁移及重复执行演练。
3. 备份、回退与恢复演练。
4. 灰度检查表、观察和回退条件。

### 规划中的验证证据与退出条件

在经批准的测试环境运行真实 HTTP、浏览器和桌面链路；模拟网络中断、刷新响应丢失、短信/供应商失败、成员退出与席位释放并发。按 C-36、C-37 可先使用 mock 完成四种登录方式的内部流程端到端验证及阶段交付；供应商和 OAuth 应用接入后补真实发送、官方授权及回跳证据，不能将 mock 结果标为已完成真实外部服务验证。

迁移验收需证明旧账号与业务数据仍可对应到正确用户，旧会话按 C-35 停止沿用，凭据接续按 D-09 的明确方案处理，没有错绑和越权；恢复演练需证明备份能实际还原到明确检查点，回退不重新接受已失效的旧会话。

内部流程与 mock 联调完成后可记录阶段交付，不因短信/邮件供应商或 Google/GitHub 应用尚未准备而否定已完成项；这与正式启用真实认证服务的发布验收分开。用于真实用户的发送和第三方登录路径须先补齐供应商与 OAuth 应用配置、实际发送及官方授权验证，并完成必要决策、恢复演练和其余首期验收，才形成可供用户批准的发布候选。**本计划不是执行真实数据维护或部署的授权。** 未取得用户当次许可前，停留在隔离演练及可审阅的发布准备，不动真实 Home、生产数据库或线上部署。

## 9. 后续独立项目

- **付费业务接入**：确定正式套餐、席位的业务功能清单与收费规则，再将权益服务接入实际执行入口。Work 复用动作发现、受理和 `beforeEffect` 复核，页面、工作流、Agent、MCP 与插件共用规则；离线付费许可和执行中撤权按 D-06 确定。

- **完善商业运营**：在套餐和计费规则明确后建设配额、账单与运营功能；多类型许可的功能并集不自动意味着配额相加。

这些项目的时间与交付范围另定，不作为本次登录接入附带完成，也不能把未建设的云共享能力写入首期验收结论。
