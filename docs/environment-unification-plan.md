# Auth、Molis Club、Molis Work 三环境统一改造方案

状态：三仓代码已落到独立工作树，已完成定向验证。远程测试与正式发布条件有缺口，整体验收未通过。

确认日期：2026-11-18（Asia/Shanghai）。

本文件是三个服务本次环境改造的统一实施与验收依据。后续任务先读本文件；执行进度、验证结果和待决事项在文末更新。不得把计划中的行为描述为已经实现。范围、认证安全边界或数据处理方式发生实质变化时，先与用户对齐，再修改本文件。

## 1. 目标与范围

同一套业务代码、同一个启动流程，显式读取不同环境的配置来决定资源连接与受控策略。只允许 `dev`、`test`、`prod` 三类环境配置。

本期工作：

- 三个服务统一配置文件格式、加载规则、启动参数、环境检查和部署配置生成。
- 明确本地与远程资源归属，支持本地单服务连接远程测试依赖。
- 支持从可信入口动态传递登录回调，登录后返回原应用页面。
- 新增 test 邮箱/手机号白名单。
- 新增切换环境强制重新登录。
- 增加 dev/test 环境标识及必要的状态隔离。
- 删除旧环境配置入口、别名、跨环境回退及对应兼容逻辑。

不在本期范围：

- 重写原有业务流程、认证协议或身份合并规则。
- 修改数据库表结构、清库、迁移已有业务数据。
- 自动删除旧云端资源或新建全部数据库。
- 在本地启动时执行远程建库、迁移、客户端注册或数据初始化。
- 为白名单增加实时踢人、会话刷新策略等复杂机制。

“重新来”最终确认含义是重新统一配置机制，不是重建数据库或删除业务逻辑。现有数据库与数据保留；其具体环境归属必须盘点确认，不能仅凭历史名称推断。底层历史资源标识不等于对外环境别名，不因改名强制重建资源。

## 2. 已确认的环境规则

| 环境 | 资源规则 | 运行方式 |
| --- | --- | --- |
| dev | 本地业务数据库、本地 Auth | 本地运行，按需启动依赖 |
| test | 优先使用远程测试数据库和测试依赖 | 支持远程部署，也支持本地单服务运行 |
| prod | 正式数据库、正式业务服务 | 正式部署；正式发行的 Work 客户端可使用 |

- 本地启动必须显式指定 `dev` 或 `test`，无默认值。
- 本地源码开发启动禁止 `prod`；这不禁止正式发行的 Work 在用户电脑上访问 prod。
- Auth 本地运行也支持 dev/test，不能人为拆成两套认证业务流程。
- 远程部署明确指定 test/prod。
- 缺少配置、鉴权失败、网络失败均报错，不自动切换环境、数据库或模拟服务。
- 三个环境全部使用真实邮件、短信、Google/GitHub 等第三方服务。
- 第三方凭据按环境独立保存，允许用户主动填写相同凭据及供应商目标；不得自动引用或回退到 prod 配置。
- 禁止本地接入 prod 指正式业务服务与数据，不禁止 test 使用相同第三方供应商。

### 2.1 固定入口

| 服务 | 本地固定地址 | 远程 test 地址 |
| --- | --- | --- |
| Auth | `http://127.0.0.1:8787` | `https://auth.test.molis.ai` |
| Club | `http://127.0.0.1:3000` | `https://test.molis.ai` |
| Work | `http://127.0.0.1:4207` | 本地客户端连接测试 Auth |

同一服务 dev/test 共用端口。切换前停止原进程，端口占用直接报错，不自动换端口。默认统一使用 `127.0.0.1`，不混用 localhost。

prod 使用经盘点确认的现有正式地址。Cloudflare Worker 公网入口使用 HTTPS/443，不虚构平台不存在的进程监听端口；自建进程部署才需要配置固定内部监听端口。

### 2.2 Work 本地存储边界

Work 的账号和云端业务资源随环境选择。本机项目文件仍留在本机；必须落地的 Home、数据库、缓存与凭据按环境隔离。这些本地运行存储不作为远程测试业务数据库的替代品。

切换环境不删除项目文件或业务数据，不自动上传本机项目。

## 3. 配置文件与唯一来源

三个仓库分别采用相同结构，各自维护自身拥有的配置：

```text
config/
  dev.properties
  test.properties
  prod.properties
secrets/
  dev.properties
  test.properties
  prod.properties
secrets.example/
  dev.properties
  test.properties
  prod.properties
```

- 普通配置入 Git；真实 secrets 文件加入忽略规则；模板不含真实密钥。
- UTF-8、`key=value`，支持注释、空行和有文档约定的转义。
- 采用合适的解析实现并明确支持范围，不未经验证宣称完整兼容 Java Properties。
- 拒绝重复键、未知键、缺少必需项、无效类型及非法枚举。
- 普通配置与密钥字段职责固定，不允许互相覆盖。
- 配置文件是唯一来源，不允许系统环境变量覆盖业务配置。
- 环境选择参数只负责选文件，不承载另一套业务配置。
- 不读取其他环境配置补齐缺项。
- 启动时加载、校验并冻结配置；修改后重启，远程修改后重新部署，不做热更新。
- 测试框架可以注入隔离夹具，但不能让生产启动路径因此获得隐式覆盖机制。

加载流程：

```text
显式环境参数 → 普通配置文件 + 同环境密钥文件
             → 严格解析与跨字段校验
             → 不可变运行配置
             → 平台绑定/服务启动
```

内部现有认证合同若仍使用 `LOCAL / TEST / PRODUCTION`，可以由适配层映射 dev/test/prod；这不新增配置环境或命令别名。是否需要更改合同字段，应按合同变更规范处理，不顺手全局替换业务枚举。

### 3.1 云端配置和注册记录

Worker 无需在运行时访问开发机上的 properties 文件。部署工具读取对应文件，生成平台变量、Secret、资源绑定及客户端登记清单。平台变量和 Secret 是部署载体，不是另一套人工维护的业务配置源。

密钥只经受控路径注入平台，不进入前端包、Work 安装包、普通配置产物或日志。正式 Work 仅携带客户端所需公开配置，服务端供应商密钥留在 Auth 等服务端。

Auth 数据库中的客户端/环境登记仍属于现有认证机制。文件声明所需配置，平台通过现有管理能力登记并核对；本地启动只检查，不自动同步写库，不删除现有安全检查。

## 4. 启动、部署和防误接

统一命令语义，落地时适配各仓库现有包管理器：

```text
start --env dev
start --env test
deploy --env test
deploy --env prod
```

以上为待实现命令契约，不表示当前已可运行。现有其他可绕开检查的启动入口必须一并梳理收敛。

启动前检查：

1. 环境显式且合法，本地开发不允许 prod。
2. 文件存在、必需字段齐全、无跨环境补齐。
3. 固定端口可用，不停止其他进程、不自动换端口。
4. 地址、客户端、回调、资源绑定与环境匹配。
5. dev/test 不得绑定已登记的正式业务数据库、正式 Auth 或正式业务服务。
6. 数据库连接及所需结构兼容；失败只报错。
7. 第三方真实服务必要配置完整，不降级为模拟。

正式资源的非敏感标识清单需由盘点得到，不能仅靠名称包含 prod 判断。防误接校验不是平台权限隔离的替代品。

启动日志显示环境、入口、Auth 目标、数据位置和非敏感资源标识。日志不输出令牌、密码、完整连接密钥。

dev/test 界面始终显示实际环境，test 默认标明远程测试数据；prod 不显示开发标识。标识来自实际加载配置，不另设可伪装环境的开关。

## 5. Cloudflare 与数据库接入

Club 保留现有 Vite + Cloudflare 插件启动方式；Auth 保留现有 Wrangler 启动方式。两者都是 Workers 平台的开发入口，不引入两套环境机制。统一配置加载器分别生成它们需要的绑定配置。

- dev：D1 本地绑定，本地持久化状态保留。
- 本地 test：优先使用 D1 `remote: true`，绑定明确的远程测试数据库。
- 云端 test/prod：分别绑定自己的业务资源。
- R2、Service Binding、Durable Object 等逐类核实，不能假设所有绑定都与 D1 一样支持远程模式。
- Auth 密码计算 Durable Object 保留现有计算实现；本地运行对应实例，不把它当成必须远程访问的业务数据库。
- 启动只检查必要结构，不执行建表、迁移、seed 或管理配置写入。
- 远程 test 数据库建库、迁移和初始化由平台管理，不增加本地启动中的维护入口。
- 正常业务请求读写测试数据仍然允许，“不改数据库”不等于禁止正常业务写入。

### 5.1 已获准的备选方案

若实际技术验证确认当前项目无法合理接入远程 D1，可让本地 test 显式使用独立本地测试库；远端其他 test 服务继续使用自己的远程资源。

启用前记录具体限制和验证证据，明确本地数据与远程数据不一致的边界。本地 test 库不得与 dev 共用。配置、日志和环境标识必须显示实际数据位置。断网、权限错误或暂时故障不能触发自动切库。

目前官方能力和本机配置解析验证均支持远程 D1，尚无启用此备选的理由。

## 6. Auth 适配与测试白名单

### 6.1 保持认证合同

复用现有客户端登记、Origin、回调允许范围、state、PKCE、事务有效期和会话校验。不得为了跑通本地 test 放宽为任意来源或跳过注册信息匹配。

本地 Auth 连接远程测试库时，其本地地址与远程 Auth 地址不同。现有代码会把运行配置与数据库登记对比，不能仅修改 `AUTH_ORIGIN` 后直接复用远程登记。

方案方向是同属 test 的不同运行入口分别登记匹配的认证配置和客户端关系，仍使用同一套业务代码及测试数据库。登记标识不是新增环境类别。须先验证现有平台管理能力、用户归属及会话隔离是否支持；若涉及表结构或身份语义变化，暂停该具体方案并与用户对齐，不擅自实施。

### 6.2 白名单

test 普通配置维护邮箱和手机号名单，沿用 Auth 的身份规范化规则；手机号采用带国家区号的规范形式。

- 在注册、登录、相关验证码发送入口统一检查，覆盖所有认证方式及可绕行入口。
- 配置启用白名单但名单为空时拒绝进入，不解释为放行所有人。
- 不允许通过找回密码等路径绕过准入或触发不允许的发送。
- 第三方登录依据已验证联系方式或已绑定的账号身份判断，不能相信用户自行提交的邮箱。
- GitHub 当前适配器不把公开邮箱作为可信邮箱。本期使用白名单邮箱/手机号先注册，再绑定 GitHub；不扩大为新的身份采集流程。
- 移除名单不主动踢出已有会话，不改变现有刷新策略；重新登录时检查新名单。
- 名单修改在重启/重新部署后生效，不引入热更新。

## 7. 动态回调与原页面恢复

“从哪来回哪去”通过现有认证事务参数实现，不在业务代码中写死本地或远程地址。

```text
可信应用入口 → 匹配配置中的已登记客户端
             → 生成准确 callback 地址
             → 传递 redirectUri、state、PKCE
             → Auth 检查登记允许范围
             → callback 验证认证结果
             → 恢复原应用内部页面
```

- test 中本地与远程的 Club、Work 按实际入口分别登记客户端，共用测试账号和数据。
- 从明确允许的访问入口选择客户端，不能直接使用用户提供的任意 clientId、Host 或转发头。
- Auth 精确校验回调允许范围，不采用任意域名或宽泛通配符。
- 应用保存登录前的内部路径，拒绝外部 URL、协议相对地址和编码绕过。
- 不把访问令牌、刷新令牌放进返回页面 URL。
- 第三方 → Auth 的回调，和 Auth → Club/Work 的回调分别处理；前者仍须在供应商后台准确登记。

Club 要允许 test 下准确的 HTTP 回环入口，同时保留远程 HTTPS 要求。同步核实 Cookie、Origin/CSRF、BFF 请求和回调消费，不仅改配置校验一处。

## 8. 切换环境强制重新登录

不能只分目录，因为切回旧环境可能恢复旧凭据。

实施方向：维护本机运行实例的最近环境与会话代次；切换时更新代次，使本机先前认证状态失效。该记录属于运行状态，不是第四份环境配置。

- dev → test、test → dev 都必须重新登录。
- 切回原环境也不能恢复旧凭据。
- Club 的本地 Cookie/会话必须匹配当前实例和代次。
- Work 除 Home 隔离外，还需防止旧 Home 凭据恢复。
- 作废当前客户端旧凭据、待完成登录事务和账号缓存。
- 取消或隔离旧环境后台任务及迟到请求，防止新状态被旧结果污染。
- 不删除项目文件、业务数据，不主动退出其他设备或其他测试人员。
- 重新发起认证事务，不通过旧产品会话或管理交接静默恢复。

Google/GitHub 可能保留自己的登录态。我们保证重新完成产品认证流程，不承诺强迫用户重新输入第三方密码，也不尝试清理供应商全局登录状态。

### 12.5 复评与执行优先级（2026-11-18）

三环境、同一业务流程、文件选取资源和精确回调的决策继续有效。本节基于当前三个开发目录的源码和上表已有验收记录。复评没有重新执行云端探针或全量测试。按以下顺序验证：

1. **先保护部署目标。** Auth 与 Club 的配置生成器校验了部分 D1 标识，但均把通过格式校验的 `workerName` 直接作为部署目标。同账号下仍可能将 test 包发布到正式 Worker。实际部署前按服务核对账户、Worker、域名路由及 D1 的完整归属，增加离线的错配拒绝用例。域名和资源标识应有统一的声明位置，逐步消除源码和 properties 中重复维护的环境值。
2. **先打通使用频率最高的一条链路。** 平台确认测试资源归属和授权后，只启动本地 Club，连接远程测试 Auth，从带查询参数的站内页面完成登录、回到原页并读取测试业务数据。再对本地 Work 执行相应的登录验收。远程测试 Auth 登记的是这两个产品的本地客户端。开发人员在本地运行 Auth 自身的 test 模式是独立场景，不应成为 Club、Work 联调的先决条件。
3. **按服务决定 D1 备选。** 通过本地 Worker 的真实绑定执行只读查询并核实测试库身份，区分平台 API 可读、开发代理可用、业务结构兼容。若代理持续不可用且确认属于集成限制，采用已批准的显式本地 test 库，独立于 dev，并在启动日志和界面显示实际数据位置。远程 Auth 与远程 Club 保持各自的测试资源。
4. **把“登录可用”和“云端业务可用”分别验收。** Work 的 dev/test 配置当前只接受空的 `syncOrigin`，本地启动也没有把同步地址传给同步模块。若要保留已有同步能力，应允许配置对应环境的同步入口，并验证一次真实同步的目标。若测试同步服务尚未提供，标注具体缺项。Work 正式安装版当前使用 4173，开发入口为 4207，正式发布前核对已有安装版、监听地址和注册回调，记录最终端口决定。
5. **把自动化证据和外部验收分开。** 白名单移除、旧会话保留、切换环境重登、同环境重启和旧回调失效可先用隔离夹具验证。再由获准的测试账号完成供应商真实链路。Work 存储通过代次改变旧凭据的查找位置，验收时区分“旧会话不可恢复”与“旧凭据记录已清理”。真实白名单邮箱、手机号属于个人联系方式，建议在部署方私有管理的 test 普通配置中维护，仓库样例使用虚构数据。

正式 Auth 缺表是上一轮只读探针的结果，影响正式发布评估。先核对线上 Worker 版本与实际 D1 绑定。测试联调可继续进行。原 ENV-01 至 ENV-20 的历史结果保留；新增的错配防护与 Work 同步场景需单列证据后再判断验收。
